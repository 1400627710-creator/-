## 一、项目定位

CardStudio 面向没有编程、专业绘图或 PS 基础的桌游作者，核心流程是选模板、填字段、复用素材、调整版式、检查质量和导出卡牌。

| 版本 | 工作定位 | 本轮交付版本 |
| --- | --- | --- |
| Studio 私人版 | 承载精细排版、类型主模板、项目检查及专业发布工作流 | 3.0.0 Beta 5.1 |
| Community 社区版 | 提供轻量制卡与共享资料能力，优先保证易用、兼容和稳定 | 1.2.2 |

共享词条与共享素材分别管理。词条表达规则语义；素材表达图像、卡框、底纹和图标等视觉资源，不能混成同一类导入、存储或导出对象。

## 二、已经形成的开发纪律

1. **交付前先真实启动和交互验证。** 语法检查与静态检查不能代替浏览器中的实际操作。
2. **真实 Bug 必须进入回归检查。** 修复后补充能覆盖问题的检查，防止后续改动再次破坏相同流程。
3. **默认界面简单，高级能力按需展开。** 围绕制卡任务安排工具，避免用功能数量代替可用性。
4. **语义对象优先。** 优先表达卡名、费用、数值徽章、规则文本、插画等制卡对象，再处理其几何矩形。
5. **批量操作先展示影响。** 类型主模板更新必须让用户知道跟随卡、局部覆盖卡、锁定卡及变化模块的范围。
6. **锁定必须具有实际冻结语义。** 不能只禁用界面按钮，却允许批量模板同步继续改动锁定卡。
7. **危险操作默认有保护，错误不得静默。** 明确拒绝超限、解释失败原因，不用静默截断伪装成成功。
8. **持续检查必须有性能预算。** 避免在拖动的每个事件上全项目扫描，快速检查与完整检查分工明确。
9. **执行沟通使用精确、简洁的中文。** 常规实现选择由开发者推进；需要用户操作时给出明确步骤。
10. **保持私人版与公开版边界。** Studio 核心保持私有；公开仓库只上传 Community 源码、通用开发日志和验证记录。

## 四、Studio 3.0.0 Beta 5

本阶段的目标是让已有专业能力更安全、更早反馈、更容易理解。

### 持续卡牌质量检查

- 舞台右上角展示通过、警告、错误及锁定状态，点击可打开完整项目检查中心。
- 快速检查覆盖编号冲突、词条与图标引用、插画 DPI、字段约束、卡名中轴和模板继承漂移。
- 精确 DOM 安全区、裁切与文字溢出仍由完整 Preflight（发布前检查）负责。
- 持续 QA（质量检查）使用 120ms 合并刷新，避免拖动时逐次全项目扫描。

### 类型模板影响预览

“设为此类型统一布局”、按毫米写入数值徽章模板、把布局组件写入类型主模板，都必须先显示影响范围。

预览包括同类型总卡数、自动跟随卡数、局部覆盖卡数、锁定冻结卡数、变化的语义模块，以及优先复核的代表卡。

### 锁定卡冻结

- `applyTemplateMaster()` 不再改动锁定卡。
- 锁定期间因主模板演进形成的几何差异，不再误报为继承漂移。
- 解锁后可通过模板校准或下一次同步跟进最新布局。

### 日志记录的新增回归脚本

`beta5-safety-check.mjs` 用于检查持续 QA、模板影响预览入口、锁定冻结契约，以及快速检查与完整检查的误报问题。首次日志归档时未取得该脚本；本轮已取回并执行通过，纳入 Studio 常规自检与一键诊断。其代码随私人包交付。

## 五、Community 1.2.1

- 共享素材库总量上限为 **120MB**，防止多次导入无限堆积 IndexedDB 数据。
- 共享素材包超过 **1000 项**时明确拒绝，取消静默截断。
- 直接读取 Studio `userAssets` 时补齐 `frameImage / textureImage / art / icon` 的角色映射，避免全部归入“其他”。
- 共享素材库统一使用 **`.csassets`** 扩展名，与词条 JSON 区分。
- 日志记录新增 `asset-library-check.mjs`，覆盖素材包格式、分类映射、去重、安全栅格限制和总量边界；首次归档时未执行；本轮已实际运行，并随 Community 源码同步。

## 六、下一阶段方向

以下是此前提出的设计方向，尚未由本次日志证明全部实现，应作为待办继续推进：

- 按“创作 → 排版 → 素材 → 检查 → 发布”收敛工作区。
- 在现有模板影响统计基础上完善代表卡的变更前后预览。
- 素材管理明确来源、用途、共享状态、引用关系与 DPI。
- AI 插画工作流采用候选队列；外部连接层与制卡编辑流程分离。
- 继续完善持续发布前检查，保持快速检查与精确检查的职责边界。
- 为卡牌建立语义版本记录，便于说明某张卡改变了什么。
- 逐步拆分存储、素材、检查、模板与 AI 模块，避免继续把全部逻辑堆入 `app.js`。

## 七、后续接续方法

1. 先读取本总记录及对应原始日志，确认当前实际源代码与安装包版本。
2. 需要继续开发新版时，先同步对应版本源代码与检查脚本，再修改实现。
3. 每次修复记录触发方式、影响范围、修改结果和实际验证情况。
4. 交付前执行适合本次改动的检查，并真实启动验证关键操作。
5. 更新对应版本日志与本总记录；计划、日志声称的完成项和实际验证结果分别写清。

原 GitHub 自检与 Windows 打包流程仍服务于 2.3.0。新增 Community 持续集成独立运行常规自检和真实 Chromium 回归；私人版的验证以本轮实际结果和私人交付包为准。
