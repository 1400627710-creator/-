1. 在当前 ChatGPT 会话选择“卡递 · 统一卡片工作台”插件。
2. 调用 `open_workbench({})`，或从插件界面入口打开工作台。
3. 用户仍观察到“无法打开 打开卡递统一工作台”；此前网站内嵌打开还显示“拒绝连接”。

预期：真实 ChatGPT 窗口打开，界面完成初始化，能载入私人项目并继续编辑。当前状态：用户明确反馈仍然失败，不能宣布修复完成。

## 目前缺少的关键证据

真实 ChatGPT 窗口“无法打开”对应的宿主错误、沙箱初始化结果和浏览器控制台/网络失败详情。此前可操作浏览器只提供隔离预览，没有用户实际 ChatGPT 应用窗口。因此不能确认资源交付后，宿主在哪一步失败。

供协作者观察：先区分错误发生在插件入口/资源载入阶段，还是 HTML 已显示后发生 ui/initialize 超时、工具代理失败、身份失败或编辑器初始化失败。请记录同一次尝试的北京时间、页面错误和对应资源/消息状态；共享前去除 Cookie、Authorization、签名参数及私人正文。

## 已尝试的修复

- 修正显示模式在 `openai/ui` 中的声明，清理旧兼容别名和多余入口属性。
- 普通网站预览与 MCP 资源使用不同标记；MCP 接入由资源标记决定，不能只看是否 iframe。
- 响应必须带 result/error，防止同窗口请求回声误当成初始化响应。
- 网站登录链接使用顶层导航；隐藏元素不再被按钮 display 样式覆盖。
- 打开工具不再返回 `opened: true`；编辑器完成初始化后才发送单独的 uiReady。

这些改动修复了已发现缺陷，但用户报告的完整打开路径仍未修通。它们都不应被当作已确认根因。

## 其他排查注意点

当前版本标识未完全统一：MCP 和界面为 1.0.3，`package.json` 仍为 0.1.0，健康接口仍返回 1.0.0。该不一致可能干扰版本判断，但没有证据表明它就是窗口打不开的原因。本次交接保留原状，没有偷偷改应用代码。

`lib/workbench-html.mjs` 约 2.26 MB；隔离浏览器能解析，但真实宿主是否接受同一资源，仍需真实错误证据，不能根据体积自行断定。
